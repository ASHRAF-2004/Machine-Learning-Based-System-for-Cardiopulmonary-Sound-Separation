\chapter{Proposed Design Patterns}
\sloppy

This chapter documents three design patterns used in the cardiopulmonary sound separation system. The roles are intentionally separated so that each pattern has its own purpose and its own main classes. \texttt{SeparationService} is explained only as the Facade. \texttt{SeparationEngine} is explained as the Strategy Context. \texttt{AudioValidatorFactory} is explained as the Factory Method Creator for upload validation. The model-selection helper \texttt{ModelStrategyResolver} supports choosing an implemented algorithm from a database model record, but it is not the Factory Method pattern discussed in this report.

\section{Facade Pattern}

The Facade Pattern provides a simplified interface to a group of related subsystem operations \parencite{gamma1994designpatterns}. In this project, it is used to keep the FastAPI separation route small while the service layer coordinates model lookup, storage paths, result recording, and job status updates.

\subsection{Pattern Type}

The Facade Pattern is a structural design pattern. It organises a complex workflow behind one higher-level interface that is easier for a client to call.

\subsection{Problem}

The separation endpoint should not directly handle model lookup, upload lookup, output path preparation, job creation, inference coordination, result persistence, and error handling. Placing all of that logic inside \texttt{SeparationRouter} would make the route difficult to test and difficult to explain in the software design report.

\subsection{Solution}

\texttt{SeparationRouter} calls \texttt{SeparationService} through one high-level operation. \texttt{SeparationService} acts as the Facade and coordinates the service-level subsystems: \texttt{ModelService}, \texttt{StorageService}, and \texttt{ResultService}. The router remains responsible for HTTP request and response handling, while the Facade owns the separation workflow.

  \item \textbf{Client:} The caller that wants to use subsystem functionality without controlling every subsystem directly.
  \item \textbf{Facade:} The simplified interface that coordinates subsystem work.
  \item \textbf{Subsystems:} The internal components that perform specialised tasks.
\end{enumerate}

\subsection{Project Application}

\subsubsection{i. Function or Software Component Affected}

The affected component is the backend separation workflow in \texttt{app/services/separation\_service.py}. \texttt{SeparationRouter} in \texttt{app/routers/separation.py} delegates the workflow to the Facade instead of coordinating subsystem details itself.

\subsubsection{ii. Description of Workflow or Data Flow}

The user starts separation from the web interface. \texttt{SeparationRouter} receives the uploaded audio identifier and optional model identifier, then calls \texttt{SeparationService}. The Facade retrieves the upload and model, prepares output paths, creates a running job, coordinates the selected real separation strategy through the engine, records the result, and returns a response containing the generated heart and lung output paths. The Facade uses the strategy and model-selection helper internally, but its pattern role remains Facade only.

\begin{lstlisting}[caption={Facade Pattern Code Example}]
class SeparationRouter:
    # Client: handles HTTP concerns only.
    def separate_audio(self, audio_id: int, model_id: int | None, db):
        return SeparationService().separate_uploaded_audio(
            db=db,
            audio_id=audio_id,
            model_id=model_id,
        )


class SeparationService:
    # Facade: coordinates subsystem calls in one workflow.
    def separate_uploaded_audio(self, db, audio_id, model_id=None):
        uploaded_audio = get_uploaded_audio(db, audio_id)
        model = ModelService.get_model_for_separation(db, model_id)
        output_paths = StorageService.build_separation_output_paths(job_id)
        result = ResultService.create_separation_result(db, job_id, output)
        return result
\end{lstlisting}

\subsubsection{vi. Benefits}

The Facade keeps route logic thin, makes the main separation use case easier to test, and gives the report a clear explanation of where workflow coordination happens. It also improves maintainability because storage, model lookup, and result persistence remain separate subsystem concerns.

\subsubsection{vii. Limitations}

The Facade can become too large if detailed validation, model internals, or result formatting are placed inside it. The implementation avoids this by keeping upload validation in its own component, model lookup in \texttt{ModelService}, output path handling in \texttt{StorageService}, and result creation in \texttt{ResultService}.

\section{Strategy Pattern}

The Strategy Pattern allows a family of algorithms to be used through a common interface \parencite{gamma1994designpatterns}. In this project, it keeps the separation engine independent from NeoSSNet internals while still using the current real NeoSSNet inference path.

\subsection{Pattern Type}

The Strategy Pattern is a behavioral design pattern. It defines a common interface for interchangeable algorithms and lets a context call the selected algorithm through that interface.

\subsection{Problem}

The backend should not spread NeoSSNet-specific inference calls across routers or service workflow code. If the workflow directly calls \texttt{run\_neossnet\_inference}, the system becomes harder to test and harder to extend when another real implemented separation algorithm is added.

\subsection{Solution}

\texttt{SeparationEngine} is introduced as the Strategy Context. It depends on the \texttt{SeparationAlgorithm} abstraction and calls \texttt{algorithm.separate(...)}. \texttt{NeoSSNetStrategy} implements the abstraction and wraps the existing real \texttt{run\_neossnet\_inference} function without duplicating NeoSSNet code.

\subsection{Structure}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.82\textwidth]{strategy_template.png}
  \caption{Strategy Pattern Template Structure}
  \label{fig:strategy-template}

\begin{enumerate}
  \item \textbf{Context:} The object that uses a strategy through a shared interface.
  \item \textbf{Strategy:} The abstraction that defines the algorithm operation.
  \item \textbf{ConcreteStrategy:} The implemented algorithm used at runtime.
\end{enumerate}

\subsection{Project Application}

\subsubsection{i. Function or Software Component Affected}

The affected component is the ML inference boundary under \texttt{app/ml/}. The relevant files are \texttt{separation\_engine.py}, \texttt{separation\_algorithm.py}, \texttt{neossnet\_strategy.py}, and \texttt{neossnet\_inference.py}.

\subsubsection{ii. Description of Workflow or Data Flow}

\texttt{SeparationService} obtains the selected model and asks \texttt{ModelStrategyResolver} for a matching \texttt{SeparationAlgorithm}. The resolver is only a model-selection helper. \texttt{SeparationService} passes the algorithm to \texttt{SeparationEngine}. The engine calls \texttt{algorithm.separate(...)} with the uploaded WAV path, model checkpoint path, model configuration path, and heart/lung output paths. \texttt{NeoSSNetStrategy} then calls the existing NeoSSNet inference function and returns output metadata.

\begin{lstlisting}[caption={Strategy Pattern Code Example}]
class SeparationAlgorithm(Protocol):
    # Strategy: small interface for real separation algorithms.
    def separate(self, input_wav_path, model_path, model_config_path,
                 heart_output_path, lung_output_path, device_name="cpu"):
        ...


class NeoSSNetStrategy:
    # ConcreteStrategy: wraps the existing real inference function.
    def separate(self, input_wav_path, model_path, model_config_path,
                 heart_output_path, lung_output_path, device_name="cpu"):
        return run_neossnet_inference(
            input_wav_path=input_wav_path,
            model_path=model_path,
            model_config_path=model_config_path,
            heart_output_path=heart_output_path,
            lung_output_path=lung_output_path,
            device_name=device_name,
        )


class SeparationEngine:
    # Context: depends on SeparationAlgorithm, not NeoSSNet internals.
    def __init__(self, algorithm: SeparationAlgorithm):
        self.algorithm = algorithm

    def separate(self, **paths):
        return self.algorithm.separate(**paths)
\end{lstlisting}

\subsubsection{vi. Benefits}

The Strategy Pattern keeps NeoSSNet code isolated, makes the engine easy to test with a mocked algorithm, and allows the service workflow to remain stable when another real separation implementation is added later.

\subsubsection{vii. Limitations}

The current prototype mainly runs NeoSSNet, so the strategy layer must remain small. Overcomplicating the abstraction would make the student project harder to maintain without improving the current working inference path.

\section{Factory Method Pattern}

The Factory Method Pattern creates products through a creator instead of forcing the client to instantiate concrete classes directly \parencite{gamma1994designpatterns}. In this project, the pattern is used for upload audio validation.

\subsection{Pattern Type}

The Factory Method Pattern is a creational design pattern. It focuses on object creation while allowing the client to work with a product interface.

\subsection{Problem}

The upload route must validate files before saving them. If \texttt{UploadRouter} directly hardcodes every validation class, adding another supported audio validator later would make the route grow and mix request handling with validation object creation.

\subsection{Solution}

\texttt{UploadRouter} asks \texttt{AudioValidatorFactory} for an \texttt{AudioValidator}. For the current prototype, the concrete product is \texttt{WavAudioValidator}, which checks the \texttt{.wav} extension and RIFF/WAVE header before the file is saved. The route depends on the product interface and keeps upload validation creation in one place.

\subsection{Structure}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.82\textwidth]{factory_method_template.png}
  \caption{Factory Method Pattern Template Structure}
  \label{fig:factory-method-template}
\end{figure}

\begin{enumerate}
  \item \textbf{Client:} The code that needs a product but should not create the concrete product directly.
  \item \textbf{Creator:} The class or method that creates the product.
  \item \textbf{Product:} The interface returned to the client.
  \item \textbf{ConcreteProduct:} The actual validation implementation created by the creator.
\end{enumerate}

\subsection{Project Application}

\subsubsection{i. Function or Software Component Affected}

The affected component is the upload workflow in \texttt{app/routers/upload.py} and \texttt{app/services/audio\_validation.py}. The upload route remains the client, and the storage service saves the file only after validation succeeds.

\subsubsection{ii. Description of Workflow or Data Flow}

The user uploads a file through the browser. \texttt{UploadRouter} calls \texttt{AudioValidatorFactory.create(file.filename)}. The factory returns \texttt{WavAudioValidator} for a WAV filename. The route calls \texttt{validator.validate(file)}. If validation fails, the route returns a bad request response. If validation succeeds, the file is saved by \texttt{StorageService} and an \texttt{UploadedAudio} record is inserted into SQLite.

\subsubsection{v. Sample Potential Code}

\begin{lstlisting}[caption={Factory Method Pattern Code Example}]
class AudioValidator(Protocol):
    # Product: small validation interface.
    async def validate(self, upload_file) -> None:
        ...


class WavAudioValidator:
    # ConcreteProduct: current WAV validator.
    async def validate(self, upload_file) -> None:
        if not upload_file.filename.lower().endswith(".wav"):
            raise ValueError("Only .wav audio files are accepted.")
        header = await upload_file.read(12)
        if header[:4] != b"RIFF" or header[8:12] != b"WAVE":
            raise ValueError("Uploaded file is not a valid WAV file.")
        await upload_file.seek(0)


class AudioValidatorFactory:
    # Creator: returns an AudioValidator product.
    @staticmethod
    def create(filename: str) -> AudioValidator:
        if filename.lower().endswith(".wav"):
            return WavAudioValidator()
        raise ValueError("Only .wav audio files are accepted.")


class UploadRouter:
    # Client: asks the creator for a validator.
    async def upload_audio(self, file, db):
        validator = AudioValidatorFactory.create(file.filename)
        await validator.validate(file)
        return await StorageService.save_uploaded_wav(file)
\end{lstlisting}

\subsubsection{vi. Benefits}

The Factory Method keeps upload validation creation separate from request handling. It also makes the validation responsibility clear in the UML: upload uses a creator and product interface, while separation model selection remains a separate helper and is not used as the Factory Method example.

\subsubsection{vii. Limitations}

Only WAV validation is currently supported, so the factory is intentionally simple. The pattern is still useful because it gives the upload workflow a clear extension point without adding unnecessary framework complexity.
